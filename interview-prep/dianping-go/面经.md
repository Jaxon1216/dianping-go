# 面经：dianping-go

> 以下为目标简历与学习口播，供掌握后选用。分析范围：`main@b5523d4` 的 Vue 3 前端、Gin API、MySQL/GORM Gen、Redis、Nginx 与 Docker Compose；已实现机制、当前边界和进阶方案分开表述。

## 项目简介（简历可用）

基于 Vue 3、Gin、MySQL 与 Redis 的本地生活点评应用，支持验证码登录、商户检索与地图找店、探店社交和优惠券秒杀；后端以分层 API 协调缓存、地理索引、时间序列与异步订单处理，并通过 Nginx 提供统一入口。

## 简历 bullet

- **请求分层与依赖组装：** handler 处理参数与 HTTP 响应，service 协调业务规则和 MySQL/Redis；Wire 在编译期生成构造调用，上层通过接口使用业务能力，HTTP 处理与业务规则分别维护。
- **Redis 会话与滑动续期：** 随机 token 对应 Redis Hash 中的精简用户，会话 TTL 30 分钟；全局中间件恢复可选身份并滑动续期，受保护路由单独鉴权，多个 Go 实例共享登录态，退出时删除会话即可主动失效。
- **商户缓存与空间检索：** 将商户详情缓存与附近候选索引交给 Redis，MySQL 保存业务事实。
  - Cache-Aside 命中直接返回，未命中回源；不存在的 ID 缓存空值 2 分钟，减少重复无效查询，更新先写 MySQL 再删除缓存。
  - Redis GEO 筛选 5 公里内的商户 ID，MySQL 批量补全详情并恢复候选顺序，分离空间检索与详情存储。
- **社交集合与 Feed 游标：** 按查询方式分别建立集合与时间索引。
  - Redis Set 保存关注集合，以交集查询共同关注；ZSet 记录点赞时间，取最近点赞用户后批量补全资料并恢复顺序。
  - Feed 用 ZSet 保存博客 ID 与发布时间，滚动读取返回最小时间戳与同分值偏移，下一次请求携带组合游标续读。
- **Lua 秒杀准入：** 将库存检查、一人一单判断、预扣库存、资格记录与 Stream 入队放入同一 Lua 脚本，避免并发请求在步骤间插入；提交消息后返回订单 ID，不等待 MySQL 落库，将 Redis 准入与数据库写入分开。
- **Stream 异步落库与事务：** Redis Stream 消费组承接准入消息，用户锁限制同一用户并发处理；在同一 MySQL 事务内查重、执行 `stock > 0` 条件扣减并保存订单，使数据库库存与订单共同提交或回滚。

## 面试问题

### Q1 项目中的一次请求如何从浏览器走到数据层？

- 对应支柱：B1
- 触发依据：“handler 处理参数与 HTTP 响应，service 协调业务规则和 MySQL/Redis”
- 考查目标：能否解释真实端到端链路、分层职责和依赖生命周期。
- 学习入口：[C01](guide-fullstack/C01-启动分层与依赖组装.md)、[C02](guide-fullstack/C02-前后端HTTP契约.md)

**面试官问题**：项目中的一次请求如何从浏览器走到数据层？

**口播版**：

我把这条链路分成客户端契约、HTTP 边界、业务用例和数据访问四层。Vue 页面只维护交互状态，通过 API 模块调用统一 Axios 实例；开发环境由 Vite、部署环境由 Nginx 把外部 `/api` 前缀去掉后转给 Gin。请求先经过日志、会话恢复等全局中间件，再由路由级鉴权决定是否必须登录。handler 只做参数绑定和 HTTP 响应，service 负责业务规则并协调 Redis 与 GORM Gen，最终按统一响应结构返回，Axios 再解包业务数据。启动时 Wire 把构造函数展开成普通 Go 调用，所以依赖关系在编译期可见，不依赖运行时反射。这个分层的结果是页面契约、鉴权规则和存储实现可以分别定位，但当前错误码仍偏粗，很多业务错误会映射成 500。

**追问 1**：你刚才说 Wire 在编译期展开依赖，和运行时 IoC 容器相比有什么取舍？

**触发依据**：主回答中的“构造函数展开成普通 Go 调用”。

**口播版**：

Wire 生成的是可阅读、可编译的构造代码，依赖缺失通常在生成或编译阶段暴露，运行时也没有容器查找和反射成本。代价是 provider 变化后要重新生成，动态替换能力弱一些。这个项目里我会同时看声明文件和生成文件：前者表达依赖意图，后者才是实际构造顺序。对可能失败的构造器，还应该返回 error 和 cleanup，让生成链能把启动失败和资源回收统一向上传递。

**追问 2**：启动时组装的依赖与后台任务，在应用退出时如何清理？

**触发依据**：主回答中的“启动时 Wire 把构造函数展开成普通 Go 调用”，继续追问依赖的退出生命周期。

**口播版**：

当前 HTTP server 会在收到终止信号后等待在途请求，最多 5 秒，但后台秒杀消费者使用无限循环和独立 background context，没有接收应用取消信号；Redis、数据库连接也没有显式 cleanup。因此 HTTP 端口停止不代表消息处理和资源都按顺序结束。完整做法是给 worker 传入可取消 context，停止拉取新消息，等待正在处理的消息完成或安全留在 Pending，再关闭连接并退出。

### Q2 为什么把登录态放在 Redis，而不是进程内存？

- 对应支柱：B2
- 触发依据：“随机 token 对应 Redis Hash”“多个 Go 实例共享登录态”
- 考查目标：会话模型、滑动过期、多实例边界与安全取舍。
- 学习入口：[C03](guide-fullstack/C03-Redis会话与滑动续期.md)

**面试官问题**：为什么把登录态放在 Redis，而不是进程内存？

**口播版**：

因为项目通过 Nginx 可以把请求分到多个 Go 实例，进程内会话要求粘性路由，而且实例重启就全部丢失。我的做法是生成随机 token，把精简用户写入 Redis Hash，并设置 30 分钟 TTL。每个请求的全局中间件先从 Redis 恢复可选身份、写入标准 request context，再刷新 TTL；需要登录的路由额外检查 context。这样公开接口也能在用户携带 token 时返回个性化状态，受保护接口又有明确安全边界。退出登录直接删除会话 key。代价是请求多一次 Redis 读写，而且 Redis 故障会影响认证，所以要监控依赖延迟和续期失败。

**追问 1**：滑动续期和固定过期有什么区别？

**触发依据**：主回答中的“再刷新 TTL”。

**口播版**：

滑动续期表达“最后一次活跃后 30 分钟失效”，活跃用户可以长期保持登录；固定过期表达“登录时刻起最多存活某个时长”。当前实现只有滑动窗口，没有绝对最长时长。如果安全要求更高，我会同时保存登录时间或绝对过期时间，续期不能超过上限，并控制续期频率，避免每个请求都写 Redis。

**追问 2**：当前验证码登录还有哪些可见风险？

**触发依据**：主回答中的“认证安全边界”。

**口播版**：

当前验证码成功后没有删除，同一个码在两分钟内可以重复换 token；验证码 key 不存在时也更像内部错误，而不是稳定业务错误。更稳妥的做法是用 Lua 原子比较并删除，防止并发重复消费，同时增加发送频控和稳定业务错误码。前端还有密码登录入口，但后端仍要求验证码且不处理密码，这属于接口契约未闭环，不能把密码登录写成已支持能力。

### Q3 商户详情缓存如何处理穿透与更新一致性？

- 对应支柱：B3
- 触发依据：“Cache-Aside”“不存在的 ID 缓存空值 2 分钟”“更新先写 MySQL 再删除缓存”
- 考查目标：缓存事实源、穿透/击穿区分、并发不一致与演进方案。
- 学习入口：[C04](guide-fullstack/C04-CacheAside与缓存一致性.md)

**面试官问题**：商户详情缓存如何处理穿透与更新一致性？

**口播版**：

我把 MySQL 定义为商户事实源，详情读取先查 Redis。正常 JSON 命中就直接返回；key 不存在时回源 MySQL并缓存 30 分钟；数据库也不存在时缓存空字符串 2 分钟，吸收同一无效 ID 的重复查询。更新时先提交 MySQL，再删除缓存，让下一次读取按需重建。这解决的是缓存穿透和常规失效，不是所有缓存问题。数据库更新成功但删缓存失败会保留旧值，读写并发也可能把旧值重新写回，所以生产化还需要删除失败重试、变更事件或版本保护，并对 TTL 加随机抖动防止集中失效。

**追问 1**：代码里已有互斥锁和逻辑过期，为什么 bullet 没写“已经解决缓存击穿”？

**触发依据**：主回答中的“不是所有缓存问题”。

**口播版**：

因为真实详情主链只调用空值缓存方案，互斥锁和逻辑过期只是未接入的备用代码，而且互斥锁实现存在未持锁也解锁、nil 目标反序列化和无界递归重试等问题。逻辑过期分支也有 goroutine 修改外层错误变量和请求取消后解锁失败的风险。简历只写已接入且行为可解释的机制，备用方案放在演进和实验里。

**追问 2**：如果业务不能接受更新后短暂读旧值，你会怎么选方案？

**触发依据**：主回答中的“并发可能把旧值重新写回”。

**口播版**：

先量化一致性窗口和写频率。强一致读取可以绕过缓存或把读写放在同一一致性存储，但延迟和容量成本会上升。多数商户详情更适合 MySQL 事务提交后发布可靠失效事件，消费者重试删除缓存，再配合短 TTL 和版本号拒绝旧值覆盖。选择依据是业务能容忍的陈旧时间，而不是一律套双删。

### Q4 附近商户为什么先查 Redis GEO 再回到 MySQL？

- 对应支柱：B3
- 触发依据：“Redis GEO 筛选 5 公里内的商户 ID，MySQL 批量补全详情并恢复候选顺序”
- 考查目标：索引与事实源分离、顺序恢复、降级语义和端到端契约。
- 学习入口：[C05](guide-fullstack/C05-GEO附近商户全链路.md)

**面试官问题**：附近商户为什么先查 Redis GEO 再回到 MySQL？

**口播版**：

GEO 适合根据经纬度快速缩小候选集，但不适合作为完整商户事实源。我在 Redis 中按商户类型保存“商户 ID + 坐标”，查询时用中心点和 5 公里半径得到 ID 与距离，再到 MySQL 批量取名称、评分等详情。SQL 的 `IN` 不保证输入顺序，所以还要按 Redis 返回的 ID 顺序重排，并把距离填入非持久化响应字段。这样空间索引和业务字段各自用合适的存储。当前索引为空时会降级为普通类型分页，但这时不再保证 5 公里语义，API 最好显式告诉客户端发生了降级。

**追问 1**：如何验证经纬度没有写反、结果确实按距离排序？

**触发依据**：主回答中的“ID + 坐标”和“距离”。

**口播版**：

我会先在接口边界固定 x 表示经度、y 表示纬度，并做范围校验；再选已知地点，用 Redis 的坐标查询和带距离搜索对照地图结果。当前预热实验把经纬度交换了，而且忽略写入错误，所以这部分还没有通过。排序也应显式指定升序，而不是依赖默认返回。最后用一组固定样本做契约测试，校验 ID 顺序和距离误差。

**追问 2**：浏览器定位成功后，当前地图为何仍可能不是“真正离我最近”？

**触发依据**：主回答中的“中心点查询”和端到端契约。

**口播版**：

页面先用默认坐标向后端加载每个类型的第一页，之后才请求浏览器定位。定位成功后只在前端重算已加载商户的距离，没有用真实位置重新查询候选集。因此它只是从“默认位置附近的有限集合”里重新排序。修复要在定位变化后重新请求，同时处理权限拒绝、请求竞态和地图资源清理。

### Q5 为什么关注用 Set，点赞和 Feed 用 ZSet？

- 对应支柱：B4
- 触发依据：“Redis Set 保存关注集合，以交集查询共同关注”“ZSet 记录点赞时间”“Feed 用 ZSet”
- 考查目标：数据结构选型、双写一致性、并发竞态与查询放大。
- 学习入口：[C06](guide-fullstack/C06-关注与点赞的数据一致性.md)

**面试官问题**：为什么关注用 Set，点赞和 Feed 用 ZSet？

**口播版**：

关注关系主要关心成员唯一性和集合交集，所以 Set 可以直接判断成员、求共同关注。点赞既要判断某用户是否点赞，又要按点赞时间取最近用户；Feed 也要按发布时间倒序，因此两者用 ZSet，member 保存用户或博客 ID，score 保存毫秒时间。MySQL 保存持久关系、博客和点赞计数，Redis 提供面向读取的集合与顺序。这个选型匹配访问模式，但当前写入是 MySQL 和 Redis 的顺序双写，不是跨存储事务；任一步失败都可能造成关系、计数和成员状态不一致，所以最终应明确 MySQL 事实源并支持重建和对账。

**追问 1**：两个并发点赞请求都看到未点赞会怎样？

**触发依据**：主回答中的“顺序双写”和“判断是否点赞”。

**口播版**：

两个请求可能都先读到成员不存在，然后都把 MySQL 计数加一，最后 ZSet 因 member 唯一只保留一个用户，计数就多了一次。可以把点赞明细放到带唯一约束的关系表，让计数成为派生值；或者用 Lua 原子切换 Redis 状态，再用可靠事件同步数据库。无论哪种方案，都要说明重试和事实源，不能只加一把锁就认为跨存储一致性解决了。

**追问 2**：热门博客列表还有什么性能问题？

**触发依据**：主回答中的“面向读取的集合与顺序”。

**口播版**：

列表取出博客后，会逐条查作者，再逐条查当前用户点赞态，一页 10 条可能多出 10 次 SQL 和 10 次 Redis 请求。我的优化会先收集作者 ID 批量查询，用 map 组装；点赞态用 Redis Pipeline 批量读取。验证不是只看代码变短，而是记录每个请求的 SQL/Redis 命令数和延迟分位。

### Q6 Feed 为什么使用时间游标加同分值偏移？

- 对应支柱：B4
- 触发依据：“最小时间戳与同分值偏移”“组合游标续读”
- 考查目标：动态数据分页稳定性、同 score 边界、写扩散与失败恢复。
- 学习入口：[C07](guide-fullstack/C07-Feed推送与滚动分页.md)

**面试官问题**：Feed 为什么使用时间游标加同分值偏移？

**口播版**：

Feed 在持续插入新数据，普通页码偏移会随新内容漂移。ZSet 按发布时间倒序后，我用上一页最小时间作为下一页上界；但毫秒时间不是唯一值，所以还要返回“上一页在这个最小时间已经消费了多少条”。下一页仍包含这个时间边界，再通过 offset 跳过已读成员，才能处理同一毫秒内多条内容而不重不漏。读取出博客 ID 后还要按 ZSet 顺序恢复 MySQL 结果。当前实现还有两处边界：返回 offset 只统计本页，若同一 score 跨多页，未累计已读数量会重复；首个 offset 又被 `required` 校验为非零，合法的 0 可能被拒绝。应在边界时间不变时累计 offset，并允许起点 0，不能把设计意图说成已完全不重不漏。

**追问 1**：发布 Feed 当前采用写扩散，有什么规模和可靠性边界？

**触发依据**：主回答中的“Feed 持续插入”和 ZSet 收件箱。

**口播版**：

普通用户写少读多，发布时把博客 ID 推给粉丝，读取会很快；但大 V 发布会产生大量串行 Redis 写入，发布延迟和部分失败概率都会上升。当前还是博客先写 MySQL、再同步推送，没有 outbox 和断点恢复，而且代码把收件箱目标取成了作者字段，真实粉丝收不到内容。修复字段后，我会把 fan-out 改成事务 outbox 加异步分批任务，并记录幂等键和进度；大 V 可改为读时合并的混合模式。

**追问 2**：怎样验证游标真的不重不漏？

**触发依据**：主回答中的“同一毫秒内多条内容”。

**口播版**：

我会构造多个相同 score 和相邻 score 的固定数据，小页大小逐页读取，收集所有博客 ID，断言集合完整、顺序正确且没有重复；再在翻页过程中插入更新数据，确认游标语义。前端也要验证它保存的是服务端返回的最小时间和 offset，而不是自己重新计算。

### Q7 为什么把资格判断、库存预扣和入队放进同一段 Lua？

- 对应支柱：B5
- 触发依据：“库存检查、一人一单判断、预扣库存、资格记录与 Stream 入队放入同一 Lua 脚本”
- 考查目标：Redis 原子边界、异步返回语义、ID 设计与异常处理。
- 学习入口：[C08](guide-fullstack/C08-秒杀资格原子判定.md)

**面试官问题**：为什么把资格判断、库存预扣和入队放进同一段 Lua？

**口播版**：

如果拆成多次请求，库存检查后可能被其他请求修改，预扣成功与入队之间也可能因进程崩溃留下库存已扣但没有消息的间隙。我把 Redis 内的库存检查、重复购买判断、扣减、用户记录和 Stream 写入放在同一脚本，Redis 执行期间不会插入其他命令，也减少网络往返。请求线程拿到成功返回后只说明资格和消息已提交，MySQL 订单还没完成。脚本原子也不等于数据库事务，更不代表运行时错误会回滚先前写入，所以库存 key 缺失、key 类型错误和集群 key 同槽都要提前处理。

**追问 1**：前端已经判断开始和结束时间，后端还需要吗？

**触发依据**：主回答中的“资格判断”。

**口播版**：

需要。前端判断只改善交互，用户可以直接调用 API。当前 Lua 只检查库存和重复购买，没有校验活动时间；券列表又没有联表补齐秒杀时间和库存，所以前端输入也未闭环。后端必须以可信时间和活动状态做最终校验，可以在 Redis 预热时写入状态或在准入前读取权威配置，并明确时钟边界。

**追问 2**：订单 ID 为什么用时间戳加 Redis 日序列？

**触发依据**：主回答中的“返回订单 ID”，继续追问该标识如何生成。

**口播版**：

高位时间让 ID 大致递增，低位日序列让多个实例在同一秒也能获得不同 ID。它不依赖数据库自增，适合请求先入 Redis、后异步落库。约束是单业务每日序列不能超过 32 位，依赖 Redis 和系统时钟，日计数 key 也应该设置过期。失败请求会消耗序列，因此只保证唯一和趋势递增，不保证连续。

### Q8 异步消费者如何保证订单与数据库库存一起提交？

- 对应支柱：B6
- 触发依据：“同一 MySQL 事务内查重、执行 `stock > 0` 条件扣减并保存订单”
- 考查目标：事务、条件更新、消息语义、幂等与 Pending 恢复。
- 学习入口：[C09](guide-fullstack/C09-Stream异步落库与事务.md)

**面试官问题**：异步消费者如何保证订单与数据库库存一起提交？

**口播版**：

消费者拿到消息后先按用户维度加锁，再开启 MySQL 事务；事务里查询同用户同券订单，用 `stock > 0` 的条件更新扣减库存，最后保存订单。三个 SQL 都使用事务绑定的 query，任何一步返回 error 都回滚。条件更新把检查和扣减放在一条 SQL 中，避免数据库库存降到负数。正确确认策略应是在业务处理成功后才 ACK，让落库前崩溃的消息留在 Pending；当前主循环在失败恢复函数返回后仍会继续 ACK，尚不能说这一控制严格成立。按至少一次处理模型设计时，数据库提交成功但 ACK 前崩溃会重放，所以持久化层仍要有 `(user_id, voucher_id)` 唯一约束，应用查询和用户锁不能替代最终约束。

**追问 1**：当前 Pending 恢复还有哪些问题？

**触发依据**：主回答中的“消息仍留在 Pending”。

**口播版**：

消费组没有在启动时幂等创建，不存在时读取会持续报错；失败处理返回后仍可能落到主循环 ACK，需要把确认与业务成功结果显式绑定；worker 只在业务处理失败后才读 Pending，重启不会优先恢复历史消息。Pending 为空时 Redis 的超时错误又被直接 continue，恢复循环可能不退出。再加上固定 consumer 名、无限重试和没有死信，永久错误会阻塞消费。完整方案要用实例唯一 consumer，启动先创建组并认领超时 Pending，设置有限重试、退避和死信，同时把 worker 绑定应用 context。

**追问 2**：Redis 已预扣但 MySQL 永久失败，如何收敛？

**触发依据**：主回答中的“事务回滚”和跨存储边界。

**口播版**：

数据库事务只能回滚 MySQL，不能自动恢复 Redis 资格。我会记录可追踪的订单状态，失败消息进入可观测的重试/死信流程，再由对账任务比较资格 Set、Stream/Pending 和 MySQL 订单。确认不可落库后，补偿脚本原子回补 Redis 库存并移除用户资格；如果订单已经存在，则按幂等成功处理。补偿也必须可重入，并防止和迟到消费者并发冲突。

### Q9 你会如何证明这些机制在并发和故障下成立？

- 对应支柱：B1、B2、B3、B4、B5、B6
- 触发依据：“避免并发请求在步骤间插入”“组合游标续读”“共同提交或回滚”等机制主张。
- 考查目标：测试分层、可观测证据、压测口径与安全实验边界。
- 学习入口：[C10](guide-fullstack/C10-部署测试与可观测验证.md)

**面试官问题**：你会如何证明这些机制在并发和故障下成立？

**口播版**：

我不会先跑一个高并发数字就下结论，而是分层验证。先做无外部写入的 Go 编译和前端构建，再为 Lua 返回码、Feed 同分游标和数据库事务写确定性测试；随后在隔离的 MariaDB/Redis 环境做 HTTP 集成。秒杀压测除了成功率和 P95/P99，还要同时核对初始库存、Redis 预扣、资格 Set、Stream/Pending、MySQL 订单数和最终库存。故障实验分别放在消费前、事务中和提交后 ACK 前，验证消息可恢复且不重复扣库存。所有结论记录环境、实例数、数据量、缓存冷热和恢复步骤。当前仓库的测试更多是会写真实 Redis 的实验入口，不能当成完整回归体系。

**追问 1**：现有日志能支撑这套验证吗？

**触发依据**：主回答中的“同时核对”和“故障实验”。

**口播版**：

HTTP 日志有 trace、请求和响应耗时，能定位同步请求，但完整记录 header、body 和 response 可能泄露 token、验证码并放大 I/O；HTTP trace 也没有进入 Stream 消息。我要先脱敏和限制 body，再把 order ID 或 message ID 作为异步关联键，补充路由状态码、依赖耗时、消费重试数、Pending 数量和死信指标。日志用于解释单次事件，指标用于发现趋势，两者不能互相替代。

**追问 2**：Nginx 配两个 Go upstream，能否直接说明系统高可用？

**触发依据**：主回答中的“实例数”和故障验证。

**口播版**：

不能。它只能说明入口具备向两个进程转发和部分连接失败重试的能力。两个实例仍共享单个 MariaDB、单个 Redis，Go 进程也不在 Compose 中，没有 readiness、自动拉起、发布回滚和存储故障切换。这个拓扑适合验证多实例共享会话和锁竞争，但生产高可用还要逐层消除单点并验证故障恢复时间。
