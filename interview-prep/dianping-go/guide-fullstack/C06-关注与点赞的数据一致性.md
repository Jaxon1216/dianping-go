# C06 关注与点赞的数据一致性

> 课程性质：核心
> 返回：[主导学](../导学.md)；前置：[C03](C03-Redis会话与滑动续期.md)、Redis Set/ZSet、MySQL 更新；下一课：[C07 Feed 推送](C07-Feed推送与滚动分页.md)
> 对应：B4；[Q5](../面经.md#q5-为什么关注用-set点赞和-feed-用-zset)；目标掌握：看懂链路、理解机制、设计与表达。

## 本课重点

场景：用户 A 关注用户 B、查询与用户 C 的共同关注，并对一篇博客点赞后查看最近点赞用户。

- 关注用 Set 支持成员判断与交集；最近点赞用户用 ZSet 保存点赞时间顺序。
- MySQL 与 Redis 是应用层顺序双写，任一侧失败都可能使关系、计数和成员状态分离。
- Redis 成员唯一不等于跨存储操作幂等；当前点赞复合操作还存在并发计数风险。

## 主链与职责

```text
关注
  -> MySQL tb_follow 保存关系
  -> Redis SADD follows:{userId} targetUserId

共同关注
  -> Redis SINTER 两个用户的 follows Set
  -> MySQL 批量查询用户资料

点赞
  -> Redis ZSCORE 判断成员是否存在
     -> 未点赞：MySQL liked + 1 -> ZADD(score=当前毫秒)
     -> 已点赞：MySQL liked - 1 -> ZREM

最近点赞用户
  -> ZREVRANGE top 5
  -> MySQL IN 查询用户
  -> FIELD 恢复 ZSet 顺序
```

MySQL 保存可持久化的关系与计数，Redis 保存集合成员和时间顺序。当前实现是应用层顺序双写，不是跨存储事务。

## 机制与边界

### Set 与 ZSet 的选型

- 关注关系只关心“成员是否存在”和“两个集合的交集”，Set 的成员唯一性和 `SINTER` 正好匹配。
- 点赞列表既要判断成员是否存在，也要按点赞时间取最近 5 人，ZSet 用 user ID 作 member、毫秒时间作 score。
- Feed 同样按发布时间排序，所以也使用 ZSet；它与点赞 ZSet 的 key 空间和业务语义不同。

### 双写一致性

关注与点赞都是“先 MySQL、后 Redis”：

- MySQL 成功、Redis 失败时，接口返回错误，但数据库已经改变。
- 重试关注可能再次插入相同关系，因为表上没有组合唯一索引。
- 共同关注完全读取 Redis，若 Set 未同步或未预热，会与 MySQL 事实不一致。
- 点赞计数来自 MySQL，而成员集合来自 Redis；任一侧失败都会造成计数与状态分离。

这类链路需要明确事实源。常见设计是 MySQL 作为最终事实，Redis 作为可重建派生数据；通过唯一约束、事务日志/消息和重建任务收敛，而不是假设两次写永远同时成功。

### 并发点赞竞态

点赞是“先读 Redis 状态，再改 MySQL，再改 Redis”的复合操作。两个并发请求可能都读取到 `redis.Nil`，都执行计数加一，再分别 ZAdd 同一个 member。最终 ZSet 只有一个成员，但 MySQL 计数增加两次。

可选演进：

- 把用户点赞事实落在有唯一约束的关系表，计数作为派生值。
- 用 Lua 原子切换 Redis 成员，再通过可靠事件更新数据库。
- 给同一“用户 + 博客”加细粒度锁，但仍要处理跨存储失败。

每种方案都必须说明事实源、重试语义和修复方式。

### 查询放大

`enrichBlogs` 对每篇博客分别：

1. 查询一次作者；
2. 若已登录，再查一次 Redis 点赞状态。

一页 10 条最多形成 10 次用户 SQL 和 10 次 Redis 查询，属于 N+1。可以批量收集 user ID 查询用户、Pipeline 批量查 ZScore，或用 JOIN/冗余快照，验证时记录实际查询次数。

### HTTP 边界

“是否关注”接口没有强制登录。全局会话恢复成功时返回真实状态，游客返回 false。这允许公开详情页展示，但 false 同时代表“未登录”和“已登录但未关注”，产品若要区分，需要额外状态。

## 需要懂什么

- **数据结构由查询方式决定。** 共同关注需要集合交集，最近点赞需要时间排序；Set 和 ZSet 分别提供这两类操作，不能因为都在 Redis 就混同语义。
- **顺序双写没有跨存储原子性。** 先写 MySQL、后写 Redis，接口报错时数据库可能已提交；重试需要唯一约束或可靠事件，否则可能重复插入或继续扩大偏差。
- **成员去重不保护计数。** 两个请求都看到未点赞时可能各给 MySQL 加一，ZSet 却只留下一个用户；最终表现为计数与成员集合不同步。
- **逐条补全会造成 N+1。** 一页内容分别查询作者和点赞态会放大 SQL 与 Redis 请求；批量取数后关联与 Pipeline 是可能的演进，当前并未普遍采用。

## 需要记住什么

- 关注关系：MySQL 保存关系，Redis Set 做成员与交集；最近点赞：ZSet 的 member 为用户 ID，score 为时间。
- 关注关系字段中 user_id 是发起者，follow_user_id 是被关注者；Feed 推送必须区分两者。
- 当前点赞：读 ZScore → 改 MySQL 计数 → ZAdd/ZRem，整体不是原子操作。
- 最终不变量应由持久化事实和唯一约束维护；当前关系表缺少组合唯一约束。
