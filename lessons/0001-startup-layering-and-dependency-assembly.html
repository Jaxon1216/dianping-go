Go 点评源码课 / Lesson 01 建议用时：15 分钟

Startup and dependency assembly

从一条启动命令，看懂对象如何被创建并连起来

本课只解决一个问题：执行 go run ./cmd/server 后，在第一个 HTTP 请求到来之前，程序到底做了什么？

完成标准

  • 能把启动期和请求期分开，不再把“注册路由”误认为“处理请求”。
  • 能解释 wire.go 与 wire_gen.go 的不同职责。
  • 能从 main 追到 ListenAndServe 与 5 秒停机窗口。
  • 能指出当前资源生命周期尚未闭环的源码证据。
先记一句 Wire 不是运行时容器。它提前生成一段普通 Go 代码，程序启动时只按这段代码创建一次依赖。

1. 先搬用你熟悉的 Express 模型

Express 中常见的手工组装

const redis = createRedis(config)
const db = createDb(config)
const service = createService(db, redis)
const handler = createHandler(service)

app.get("/user/:id", handler.getUser)
app.listen(8081)

本项目生成后的 Go 组装

client := service.NewRedis(conf)
db := service.NewDB(conf, logger)
query := service.NewQuery(db)
svc := service.NewService(
  logger, conf, query, client, redsync,
)
httpServer := server.NewHTTPServer(...)
app := newApp(httpServer)

相同点：都在监听端口前创建共享对象并注册路由。不同点：Go 用静态类型检查构造参数，Wire 只是替你生成右侧这段连接代码。

2. 最重要的切分：启动期 vs 请求期

启动期只执行一次

  • 读取配置，创建 logger。
  • 连接 Redis 和 DB，创建 Query。
  • 创建 Service、Handler 和 HTTP Server。
  • 登记中间件与路由。
  • 监听端口并等待请求。

请求期每次请求执行

  • Gin 根据方法和路径匹配路由。
  • 依次执行全局与局部中间件。
  • 调用已保存的 Handler 方法。
  • Handler 调用已注入的 Service。
  • 写回 HTTP 响应。
常见误区 s.GET("/user/:id", userHandler.QueryUserByID) 在启动期登记映射；只有请求到来后，右侧方法才会执行。

3. 按真实执行顺序读源码

  1. 入口准备。 main.go:39-56 解析 -conf，读取 Viper 配置，创建日志，然后调用 wire.NewWire(conf, logger)。

  2. 查看生成代码。 wire_gen.go:24-51 是正常构建真正编译的文件。这里可以逐行看到 Redis、DB、Query、 Service、Handler、Server 和 App 的创建。

  3. 基础设施 fail-fast。 service.go:37-68 连接 DB；Redis 创建后立即 PING。失败时 panic，应用不会带病启动。

  4. 接口隔离上层。 user.go:21-86 的构造器返回 UserService 接口； handler/user.go:11-23 只保存这个能力集合，不依赖具体 userService 类型。

  5. 注册 HTTP 规则。 internal/server/http.go:24-185 创建 Gin Engine，挂全局中间件，并登记所有路由。此时还没监听端口。

  6. 进入运行期。 app.go:39-73 在 goroutine 中调用 Server 的 Start，主 goroutine 等待退出信号。

  7. 真正监听。 pkg/server/http/http.go:43-62 创建标准库 http.Server，再调用 ListenAndServe。

4. Wire：声明文件不等于执行文件

wire.go：告诉生成器“有什么”

var serviceSet = wire.NewSet(
  service.NewDB,
  service.NewQuery,
  service.NewRedis,
  service.NewService,
  service.NewUserService,
)

这是 provider 集合。顺序不是“强制执行清单”，依赖关系来自每个函数的 参数类型和返回类型。

wire_gen.go：程序实际“怎么做”

client := service.NewRedis(conf)
db := service.NewDB(conf, logger)
query := service.NewQuery(db)
redsync := service.NewRedSync(client)
service := service.NewService(
  logger, conf, query, client, redsync,
)

这是普通 Go 代码。运行时没有容器查找、装饰器扫描或反射注入。

构建标签是关键 wire.go 带 //go:build wireinject； wire_gen.go 带 //go:build !wireinject。 正常构建选择生成文件，运行时不会执行 wire.Build 里的 panic。

5. “谁拥有谁”要从字段与构造参数看

Service
  ├─ query  *query.Query
  ├─ rdb    *redis.Client
  └─ rs     *redsync.Redsync

UserHandler
  └─ userService service.UserService

App
  └─ servers []server.Server

依赖方向是 Handler → Service → Query/Redis。页面不会直接操作 DB，Handler 也不应该承载业务规则。接口只隔离“能力边界”，并不意味着每一层都必须再包一层接口。

6. 退出链路与当前边界

SIGINT / SIGTERM
  → App.Run 的 signal channel 收到信号
  → 依次调用 srv.Stop(ctx)
  → HTTP Server.Shutdown(5 秒超时)
  → 停止接收新连接并等待活动请求
  • 确定边界： wire_gen.go 返回的 cleanup 当前是空函数， 没有关闭 DB 与 Redis。
  • 确定风险： 秒杀消费者在构造器里启动无限 goroutine，并使用 context.Background()，没有接入 App 生命周期。
  • 确定风险： Lua 文件读取失败时构造器返回 nil 接口，没有返回 error，错误会延后暴露。
  • 表达边界： 因此只能说“HTTP 有 5 秒优雅停机”，不能说“整个应用已经优雅退出”。
