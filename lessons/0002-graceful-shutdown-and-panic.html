Shutdown, panic and error

服务一直运行，但必须为“怎样退出”做好准备

部署新版本、执行 Ctrl+C、容器迁移或机器重启，都会要求进程退出。 优雅停机解决的不是“要不要停”，而是“必须停时怎样少丢工作”。

先用饭店关门理解

强制停止

直接拉闸。门口不再进人，正在吃饭的顾客也被立刻赶走。

kill -9
进程立即消失
在途请求连接中断

优雅停机

先挂“停止接客”，让店内顾客结账，再关设备、锁门离开。

停止接收新请求
等待在途请求完成
停止后台任务并关闭连接
进程退出
一句话定义 优雅停机是一个有顺序、有等待上限的退出协议，不是让服务永远不停止。

服务为什么会被要求停止

  • 开发时按 Ctrl+C，操作系统发送 SIGINT。
  • 发布新版本时，旧进程收到 SIGTERM，新进程接管流量。
  • 容器扩缩容、节点维护或机器关机，旧实例必须退出。
  • 配置或依赖初始化失败时，服务应该拒绝启动，而不是继续提供残缺能力。

本项目的 HTTP 停机链路

  1. app.go:44-45 注册监听 SIGINT 和 SIGTERM。

  2. app.go:56-63 阻塞等待信号； 服务平时“持续运行”，本质上就是这里一直没有等到退出事件。

  3. 收到信号后，app.go:65-71 调用每个 Server 的 Stop。

  4. http.go:64-76 创建 5 秒超时上下文，再调用 s.httpSrv.Shutdown(ctx)。 

SIGTERM
  → App.Run 收到信号
  → srv.Stop()
  → http.Server.Shutdown(5 秒)
  → 关闭监听入口和空闲连接
  → 等待正在处理的请求结束
  → 返回 main，执行 cleanup，进程退出

HTTP Shutdown 到底做什么

它会做

  • 关闭 HTTP 监听入口，不再接收新连接。
  • 关闭空闲连接。
  • 等待活动连接中的请求处理完成。
  • 所有活动请求结束后返回。

它不会做

  • 不会替你停止任意后台 goroutine。
  • 不会替你关闭 Redis、DB 等业务资源。
  • 不会无限等待；项目给它的上限是 5 秒。
  • 超时后只会返回 error，由调用方决定下一步。
本项目的边界 秒杀消费者使用无限循环和 context.Background()， 没有收到 App 的取消信号。因此当前只能说“HTTP 请求有优雅停机”， 不能说“整个应用已经优雅停机”。

panic(err) 是什么效果

可以先把它类比成 JavaScript 的 throw，但 Go 的 panic 更常用于“当前流程已经无法合理继续”的情况。 

if err != nil {
    panic(err)
}

  1. 当前函数从 panic 这一行立即停止正常执行。

  2. 按后进先出顺序执行已经注册的 defer。

  3. 继续向调用者退栈；没有 recover 就一直向上展开。

  4. 打印 panic 值与调用栈，进程以非零状态退出。

所以 [main.go:63-65] 的意思是：如果依赖组装返回错误，就不要打印 “server start”，也不要进入 app.Run，直接判定启动失败。

映射到当前项目的两个细节

NewWire 返回 error

当前 main 会先执行 defer cleanup()，再检查 error。 只有失败路径保证返回非 nil cleanup 时，这个顺序才可靠。

构造器内部直接 panic

例如当前 NewRedis 失败会在 wire.NewWire 内部 panic，main 还没执行到 defer cleanup()，这个清理函数不会被注册。

确定风险与当前事实 更稳妥的通用顺序是先检查 error，再注册 defer cleanup()， 避免失败时对 nil cleanup 建立延迟调用。当前生成的 NewWire 最后固定返回 nil error； Redis、DB 初始化失败走的是构造器内部 panic。因此 main.go:63-65 目前主要是为将来返回 error 的构造器保留的统一检查。

三者不要混

error
  = 一个普通值，调用方可以判断、重试、返回 HTTP 错误

panic
  = 中断当前正常流程并退栈；未 recover 则整个进程退出

Shutdown
  = 已计划的退出流程，先停止入口，再等待和清理
