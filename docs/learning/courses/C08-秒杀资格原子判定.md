# C08 秒杀资格原子判定

> 课程性质：核心
> 返回：[主导学](../roadmap.md)；前置：[C03](C03-Redis会话与滑动续期.md)、Redis Lua、位运算；下一课：[C09 Stream 异步落库](C09-Stream异步落库与事务.md)
> 对应：B5；[Q7](../interview.md#q7-为什么把资格判断库存预扣和入队放进同一段-lua)；目标掌握：看懂链路、理解机制、设计与表达。

## 本课重点

场景：大量已登录用户同时抢同一张券，同一用户也可能重复点击。

- 库存检查、一人一单判断、预扣和入队在同一 Lua 脚本中执行，避免其他请求在步骤间插入。
- API 返回订单 ID 代表 Redis 准入与消息提交完成，不代表 MySQL 已落库。
- Lua 原子执行不等于错误回滚，也不覆盖跨存储一致性；当前服务端还缺少抢券时间校验。

## 主链与职责

```text
POST /voucher-order/seckill/:id
  -> 登录中间件恢复 userId
  -> RedisWorker 生成全局趋势递增 orderId
  -> Redis Lua：
       GET seckill:stock:{voucherId}
       SISMEMBER seckill:order:{voucherId} userId
       DECR stock
       SADD userId
       XADD stream.orders order fields
  -> 0：返回 orderId
     1：库存不足
     2：重复购买
```

请求线程只完成“资格准入、Redis 预扣与消息提交”，不等待 MySQL 落库。真正订单由 C09 的消费者处理。

## 机制与边界

### Lua 解决的原子性

Redis 在执行脚本期间不会插入其他客户端命令，因此“检查库存、判断重复、预扣、记录用户、入队”不会被其他秒杀请求从中间打断。这同时减少了客户端与 Redis 的多次网络往返。

边界必须讲清：

- 它只覆盖 Redis 内的这些命令，不覆盖 MySQL。
- Redis Lua 运行时错误不会像数据库事务那样自动撤销已经执行的写命令。
- 脚本成功表示消息已写入 Stream，不表示消费者已经落库。

当前脚本先做所有可能失败的读取和类型转换，再执行写入会更安全；还应预先验证 key 类型和库存 key 是否存在。

### 当前脚本的异常边界

- 库存 key 缺失时，`GET` 返回 nil，`tonumber(nil)` 仍为 nil，继续与 0 比较会触发 Lua 错误；接口返回内部错误。
- 脚本不检查开始/结束时间。时间限制只在前端按钮里，直接调用 API 可以绕过。
- key 在脚本中由字符串拼接产生，没有通过 `KEYS` 传入。单机 Redis 可运行，但 Redis Cluster 下多 key 脚本需要同槽设计和明确 key 传参。
- Redis 扣库存和记录用户后，如果消息长期无法消费，资格状态不会自动补偿。

### 订单 ID 结构

ID 由两部分按位拼接：

```text
高位：当前 Unix 秒 - 固定起始时间
低 32 位：Redis 对“业务前缀 + 日期”执行 INCR
```

效果是多个实例共享序列，ID 大致随时间增长，适合作为分布式订单主键。约束包括：

- 单业务单日序列不能超过 `2^32 - 1`；
- 依赖 Redis 可用和系统时钟不过度回拨；
- 日计数 key 当前没有 TTL，会长期积累少量 key；
- 趋势递增不等于严格连续，失败请求也会消耗 ID。

### 前端券信息尚未闭环

券列表只查询 `tb_voucher`，没有关联 `tb_seckill_voucher`。模型中的 `stock/beginTime/endTime` 又标为 `gorm:"-"`，因此列表响应无法从当前查询得到真实秒杀库存与时间。前端按钮虽然实现了时间和库存判断，但输入数据契约未完整接通。

新增秒杀券也是 MySQL 两次保存再写 Redis，未放在事务或补偿流程中；任一步失败都可能留下部分状态。

## 需要懂什么

- **原子边界必须覆盖预扣与提交消息。** 如果先扣库存再由客户端另发入队命令，中途断连就可能留下无消息的预扣；同一脚本消除客户端多次调用间隙，但脚本运行时错误仍可能保留已执行写入。
- **受理与最终成功不是同一状态。** Lua 成功后消费者才执行数据库事务，订单 ID 只是关联标识；最终状态查询或通知是需要另行完成的能力。
- **Redis 资格约束不能代替数据库幂等。** 消息重放、数据重建与人工补偿都可能重复落库，持久化层必须独立维护订单唯一性。
- **趋势递增 ID 依赖时间与共享序列。** 高位相对秒时间、低 32 位日计数减少跨实例冲突；这不代表严格连续，也不消除时钟回拨和序列容量约束。

## 需要记住什么

- Lua 主链：检查库存 → 判断用户资格 → DECR → SADD → XADD；返回 0/1/2 分别代表准入、库存不足、重复购买。
- 请求成功只到消息提交；MySQL 落库见 C09。
- ID 由相对时间戳高位与日序列低 32 位组成；失败请求也可能消耗 ID。
- 当前缺口：库存 key 缺失会报错，时间只在前端检查，Cluster 同槽与跨存储补偿尚未处理。
