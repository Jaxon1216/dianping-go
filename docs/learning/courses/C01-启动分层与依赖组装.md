# C01 启动、分层与依赖组装

> 课程性质：核心
> 返回：[主导学](../roadmap.md)；前置：Go package、interface、pointer；下一课：[C02 前后端 HTTP 契约](C02-前后端HTTP契约.md)
> 对应：B1；[Q1](../interview.md#q1-项目中的一次请求如何从浏览器走到数据层)；目标掌握：看懂链路、理解机制、设计与表达。

## 本课重点

场景：执行 `go run ./cmd/server -conf config/local.yml`，然后访问根路径或任一 API。

- 启动期先读取配置、创建基础设施，再组装 service、handler 与 HTTP server；路由只在启动时注册。
- Wire 在编译期生成普通 Go 构造调用，运行时不做反射查找。
- 当前只有 HTTP 请求享有 5 秒停机窗口，数据库连接与后台消费者尚未统一清理。

## 主链与职责

```text
main
  -> 读取 Viper 配置
  -> 创建 Zap 日志
  -> Wire 生成代码按依赖图创建 Redis / DB / Query
  -> 创建 Service -> Handler -> Gin HTTP Server
  -> App.Run 并发启动 Server
  -> ListenAndServe 接收请求

SIGINT / SIGTERM
  -> App.Run 收到信号
  -> HTTP Server.Shutdown，最多等待 5 秒
```

Wire 类似前端构建期的依赖图展开：开发者声明“哪些构造函数可以提供什么类型”，生成代码把调用顺序写死。它不是运行时容器，也不会在每次请求时反射查找依赖。

## 源码阅读

1. [`cmd/server/main.go`](../../../cmd/server/main.go)：从 `main` 看配置、日志、`wire.NewWire` 与 `app.Run` 的顺序。
2. [`cmd/server/wire/wire.go`](../../../cmd/server/wire/wire.go)：看 provider set 如何声明 DB、Redis、service、handler 和 server。
3. [`cmd/server/wire/wire_gen.go`](../../../cmd/server/wire/wire_gen.go)：看生成后的真实构造顺序。理解项目行为时，以这个可编译文件为准。
4. [`internal/service/service.go`](../../../internal/service/service.go)：`NewDB` 创建 GORM 连接，`NewRedis` 在启动期执行 `PING`，失败直接 panic。
5. [`internal/server/http.go`](../../../internal/server/http.go)：Gin engine、全局中间件和业务路由都在启动时注册。
6. [`pkg/app/app.go`](../../../pkg/app/app.go) 与 [`pkg/server/http/http.go`](../../../pkg/server/http/http.go)：看 server 在 goroutine 中启动、信号等待和 5 秒 HTTP 优雅停机。

关键依赖顺序可以从生成代码直接读出：

```go
client := service.NewRedis(viperViper)
db := service.NewDB(viperViper, logger)
query := service.NewQuery(db)
serviceService := service.NewService(logger, viperViper, query, client, redsync)
// 再创建具体 service、handler 和 HTTP server
```

这段顺序回答了“谁拥有谁”：共享基础设施先创建，业务 service 持有它们，handler 只依赖业务接口，server 再持有 handler。

## 机制与边界

### 分层为何有价值

- handler 负责 HTTP 语义，service 负责业务规则，query/Redis 负责存储访问。新增调用端时，业务规则不必复制进页面或路由。
- service 构造器返回接口，上层只知道能力集合；这与 TypeScript 的结构化类型相似，但 Go 在编译期隐式检查具体类型是否实现接口。
- GORM Gen 把表字段和查询表达式生成成 Go 类型，减少手写字符串字段，但生成代码仍然受数据库 schema 约束。

### 当前实现的确定边界

- `NewRedis` 和 `NewDB` 采用 fail-fast；依赖不可用时不会对外提供退化服务。
- Wire 生成的 `cleanup` 是空函数，数据库连接和 Redis client 没有在退出时显式关闭。
- HTTP server 有 5 秒 `Shutdown`，但秒杀消费者用无限循环和 `context.Background()`，没有绑定应用生命周期；HTTP 停止不等于后台 goroutine 已停止。
- `App.Run` 只记录 server 启动错误，主协程不会因某个 server 启动失败自动取消其他 server。
- `NewVoucherOrderService` 加载 Lua 文件失败会返回 `nil`，构造签名没有 error；后续可能把 nil service 注入 handler，而不是启动时给出清晰错误。

这些不是“分层无效”，而是资源生命周期和构造错误契约还未闭环。

## 需要懂什么

- **依赖方向决定职责边界。** handler 面向 service 接口处理 HTTP，service 协调业务与存储；接口让 HTTP 层可以替换业务实现，不意味着底层基础设施也必须全部抽象。
- **Wire 的依赖注入发生在生成期。** provider 声明构造关系，生成文件决定运行时调用顺序；程序启动后执行的是普通函数调用，不是每个请求都查询容器。
- **优雅停机是资源与任务的整体协议。** HTTP 停止接收新请求只是其中一步；后台 goroutine、消息确认、连接关闭和等待顺序也必须有生命周期契约。当前实现尚未完成这些步骤。

## 需要记住什么

- 主链：配置 → Redis/DB → Query → Service → Handler → HTTP Server → App.Run。
- Redis/DB 初始化失败采用 fail-fast；当前 Lua 构造失败返回 nil，是另一种尚未统一的错误契约。
- Wire 生成代码是真实构造顺序；cleanup 目前为空。
- HTTP Shutdown 等待上限为 5 秒；不能据此宣称整个应用已优雅退出。
