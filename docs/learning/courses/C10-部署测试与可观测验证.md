# C10 部署、测试与可观测边界

> 课程性质：核心
> 返回：[主导学](../roadmap.md)；前置：C01-C09；下一课：回到[面经](../interview.md)完成口播

## 本课重点

场景：从部署配置、日志和测试入口理解项目的运行条件，以及现有证据能够支持哪些结论。

- Compose 只定义 MariaDB、Redis 和 Nginx；Go 双实例与前端产物需要另行启动或部署。
- 两个 upstream 不等于生产高可用，两个应用进程仍共享单点存储。
- 编译、集成状态、并发正确性和性能数据是不同证据，不能互相替代。

## 主链与职责

当前本地拓扑是混合运行：

```text
浏览器
  -> Vue Vite :5173（开发）或待部署的 dist 静态资源
  -> /api
  -> Nginx 容器 :8080（可选）
  -> host.docker.internal:8081 / :8082
  -> 两个宿主机 Go 进程
  -> MariaDB 容器 :3306 + Redis 容器 :6379
```

Compose 只定义 MariaDB、Redis 和 Nginx。Go 进程要分别使用 `local.yml/local2.yml` 或 `prod.yml/prod2.yml` 启动；前端构建产物也没有挂载到 Nginx。

理解质量证据时要区分以下层次：

```text
静态编译 -> 单元级机制 -> 存储集成 -> HTTP 契约
-> 多实例/并发 -> 故障恢复 -> 性能测量
```

每层回答不同问题：编译说明类型可用，集成说明边界协作，故障恢复与性能还需要独立证据。

## 机制与边界

### 负载均衡不等于高可用

Nginx upstream 能把请求分配到 8081/8082，并在连接错误或超时时尝试其他节点。但：

- 两个 Go 进程共享同一 MariaDB 和 Redis，存储仍是单点。
- Nginx `depends_on` 只控制容器启动顺序，不检查数据库 ready。
- Go 不在 Compose 中，Nginx 启动成功时 upstream 可能都不存在。
- 没有健康检查接口、发布编排或自动回滚。

它适合学习多实例会话共享与代理路径，不应包装为生产高可用架构。

### 日志的可观测价值与风险

请求中间件生成 trace，记录方法、URL、header 和 body；响应中间件记录完整 body 和耗时。这能串起单次 HTTP 请求，但目前：

- Authorization header、验证码、登录请求和响应数据可能进入日志。
- 大请求/响应会被完整复制，增加内存和 I/O。
- trace 只覆盖 HTTP，同一订单进入后台 Stream 后没有继续传播。
- 只有字符串耗时，没有结构化 status、route、依赖耗时和指标聚合。
- UUID 生成失败时请求中间件直接 return，未继续调用后续链路也未返回明确错误。

演进应做字段脱敏、body 大小上限、按路由采样，并把 order ID/message ID 作为异步关联键。

### 现有测试不是自动化质量闭环

- `test/app` 的 `TestMain` 启动即连接真实 Redis；多个测试会写 key。
- ID 实验启动 300 个 goroutine，每个生成 100 个 ID，但只打印、不检查唯一性。
- HLL 实验写入 100 万个值，没有执行 `PFCOUNT` 和误差断言。
- GEO 预热存在坐标交换且忽略 `GeoAdd` error。
- RedSync 实验依赖默认未启动的 6380/6381。
- 业务 handler/service 没有隔离单元测试，关键并发边界也没有回归测试。

所以可以说“存在集成实验入口”，不能说“已有完整自动化测试体系”。

### 压测结果需要契约

JMeter 文件提供 1000 线程缓存/秒杀场景，但含固定券 ID、空 Authorization、个人绝对 token 文件路径和结果树监听器。执行前必须参数化并准备隔离数据。

至少记录：

- 环境：CPU、内存、Go/Redis/MariaDB 版本、实例数。
- 数据：库存、用户数、缓存冷/热、消费组与历史 Pending。
- 负载：并发、持续时间、到达模型。
- 指标：成功/业务拒绝/系统错误、P50/P95/P99、吞吐。
- 正确性：Redis 库存、资格 Set、Stream/Pending、MySQL 库存和订单唯一性。

## 需要懂什么

- **运行拓扑要区分配置与实际进程。** Nginx 写了两个端口不代表进程已运行；depends_on 控制启动顺序，也不保证数据库已就绪。当前部署适合学习代理和共享会话，不能包装为完整发布体系。
- **可观测性必须连接状态变化。** HTTP trace 帮助定位请求，但异步消费者需要通过订单或消息标识显式关联；完整记录 header/body 还会泄露凭据并增加 I/O，当前没有完整脱敏与体积控制。
- **测试入口不等于正确性断言。** 现有测试会连接真实 Redis，部分只打印不检查；编译通过仅说明语法与类型可用，不能证明 Feed、订单或故障恢复成立。
- **性能与正确性分开判断。** 延迟、吞吐之外，还要解释库存、资格、消息与最终订单是否一致；缺少环境、负载、数据量和基线的数字不能用于比较收益。

## 需要记住什么

- 拓扑：浏览器 → Vite 或 Nginx /api rewrite → 宿主机 Go :8081/:8082 → MariaDB/Redis。
- 当前日志主要覆盖 HTTP；异步订单关联、敏感字段脱敏与结构化指标是后续方向。
- 历史构建记录不等于功能回归；仓库 JMeter 文件是入口，不是已取得的压测结果。
- 秒杀关键不变量：数据库库存不为负、同用户同券唯一、订单与库存共同提交、未完成消息可恢复；当前并非全部已保障。
